## 1. 目的

本要件定義書は、株式会社アリガトサンのコーポレートサイトに WebMCP（Web Model Context Protocol）を導入し、ブラウザ内の AI エージェントが、サイトの公開情報取得、実績検索および問い合わせ支援を、構造化された手段で安全かつ正確に実行できる状態を定義するものである。

導入により、AI エージェントが画面上の文言や DOM 構造を推測して操作する方式への依存を減らし、以下を実現する。

- サービス情報を正確かつ簡潔に取得できること
- ユーザーの課題に関連する公開実績を検索できること
- 問い合わせ内容を既存フォームへ正しく入力できること
- 制作・開発依頼および見積・相談は、ユーザーの明示承認後に送信できること
- 営業・売り込み等は自動送信せず、ユーザー自身の送信操作を必須とすること
- WebMCP 未対応環境では既存サイトが従来どおり動作すること

## 2. 背景

対象サイトは Next.js 16（App Router）および React 19 で構築され、以下の既存機能・データを有する。

- `src/data/services.ts`：サービス情報
- `src/data/works.ts`：実績情報とアクセス層
- `src/app/(site)/contact/page.tsx`：公開問い合わせフォーム
- `src/app/api/contact/route.ts`：問い合わせ送信 API
- `src/app/(site)/layout.tsx`：公開サイト共通レイアウト
- Supabase：ニュースおよび管理機能のデータ基盤
- Resend：問い合わせ通知および自動返信メール

WebMCP は本書作成時点で提案中の Web 標準であるため、既存機能を置き換えず、対応環境にだけ機能を追加する Progressive Enhancement として実装する。

## 3. 用語

| 用語 | 定義 |
|---|---|
| WebMCP | Web ページがブラウザ内 AI エージェントに構造化ツールを公開する仕組み |
| ツール | 名前、説明、入力スキーマおよび実行処理を持つ、AI エージェント向け機能 |
| 読み取りツール | サーバーまたはブラウザの永続状態を変更しないツール |
| 更新ツール | 問い合わせ送信等、外部状態を変更するツール |
| 準備 | 問い合わせフォームに値を設定し、ユーザーへ確認可能な状態で表示すること |
| 明示承認 | 送信対象、問い合わせ種別、氏名、メールアドレス、本文、プライバシーポリシーを画面表示したうえで、ユーザーが承認ボタンを操作すること |
| 自動送信 | 明示承認の操作を契機として、追加の入力を要求せずシステムが問い合わせ API を実行すること |
| 手動送信 | ユーザーが通常のフォーム送信ボタンを操作して送信すること |
| Origin Trial | 試験提供中の Chrome Web Platform 機能を登録済み origin で利用する仕組み |
| PII | 氏名、メールアドレス、電話番号等の個人を識別し得る情報 |

## 4. 基本方針

1. WebMCP は既存 UI と既存 API の補助層として実装し、WebMCP 専用の別サイトは作成しない。
2. 現行仕様に従い `document.modelContext` を使用する。
3. WebMCP が存在しない環境ではツール登録を行わず、エラーを表示しない。
4. 公開サイトのレイアウト内だけでツールを登録し、`/admin` 配下では登録しない。
5. ツール数は目的が重複しない最小構成とする。
6. 問い合わせ本文から同意を推定してはならない。
7. 更新操作は、サーバー側で入力検証、実行ポリシー判定、レート制限および重複防止を行う。
8. AI エージェントによる完全無確認送信は実装しない。
9. 問い合わせ種別に応じた送信可否は、プロンプトやツール説明ではなく、アプリケーションコードおよびサーバー側ポリシーで強制する。
10. WebMCP の停止後も、通常の閲覧、実績表示および問い合わせ送信を継続できるようにする。

## 5. 対象範囲

### 5.1 対象

- 公開サイト共通の WebMCP ツール登録基盤
- サービス情報取得ツール
- 関連実績検索ツール
- 問い合わせ準備ツール
- 明示承認後の依頼・見積問い合わせ送信
- 問い合わせ種別の追加
- WebMCP 用 API、スキーマ、型定義
- セキュリティ、監査ログ、レート制限、重複送信防止
- ローカル、ステージング、本番環境での検証
- Chrome Origin Trial の登録と配信
- 機能フラグ、段階公開、監視および緊急停止
- 単体テスト、結合テスト、E2E テスト、AI ツール選択評価

### 5.2 対象外

- Remote MCP サーバーの構築
- ChatGPT 等の特定サービスとの個別連携
- WebMCP 未対応ブラウザへのポリフィルによる疑似対応
- `/admin` 配下のニュース作成・編集・公開操作
- 「アリガトくんチャット」自体の WebMCP ツール化
- AI によるプライバシーポリシー同意の代行
- ユーザー承認のない問い合わせ自動送信
- 問い合わせ以外の契約、決済、発注確定
- WebMCP 導入のみを根拠とする SEO 効果保証

| 見積希望者 | 関連実績を確認し、見積・相談を送信する |
| 営業担当者 | 営業・売り込み内容をフォームへ準備し、自身で送信する |
| 求職者 | 採用問い合わせを準備し、自身で送信する |
| 協業希望者 | 協業・パートナー問い合わせを準備し、自身で送信する |
| 取材・その他の問い合わせ者 | 問い合わせを準備し、自身で送信する |
| サイト運用担当者 | 利用状況、失敗率、不正利用を監視し、必要時に機能を停止する |

## 7. 全体ユースケース

### UC-01 サービス情報を確認する

1. ユーザーがブラウザ内 AI に対応可能な業務を質問する。
2. AI が `get_company_services` を実行する。
3. システムが公開中のサービス情報と詳細ページ URL を返す。
4. AI が取得結果をユーザーへ説明する。

### UC-02 関連実績を検索する

1. ユーザーが課題、業界または希望サービスを伝える。
2. AI が `find_case_studies` を実行する。
3. システムが条件に合う公開実績を最大 5 件返す。
4. AI が該当実績をユーザーへ提示する。

### UC-03 制作・開発依頼を送信する

1. AI が `prepare_contact_inquiry` を `project_request` で実行する。
2. システムが問い合わせフォームを入力し、確認 UI を表示する。
3. ユーザーが問い合わせ種別、連絡先、本文およびプライバシーポリシーを確認する。
4. ユーザーが「内容を確認して送信を許可」操作を行う。
5. システムが承認対象の内容と現在の送信内容が一致することを確認する。
6. システムが問い合わせ API を実行する。
7. 送信成功後、完了画面を表示する。

### UC-04 見積・相談を送信する

UC-03 と同一フローとし、問い合わせ種別を `estimate_consultation` とする。

### UC-05 営業・売り込みを準備する

1. AI が `prepare_contact_inquiry` を `sales_solicitation` で実行する。
2. システムがフォームを入力する。
3. 自動送信向けの承認 UI は表示しない。
4. ユーザーが内容とプライバシーポリシーを確認する。
5. ユーザー自身が通常の送信ボタンを操作する。

### UC-06 採用・協業・取材・その他を準備する

UC-05 と同一フローとし、各問い合わせ種別に応じた表示を行う。

## 8. 問い合わせ種別と実行ポリシー

問い合わせ種別は、問い合わせフォーム上の選択項目および API の必須項目として追加する。

| 値 | 表示名 | WebMCP による準備 | 明示承認後の自動送信 | 通常の手動送信 |
|---|---|---:|---:|---:|
| `project_request` | 制作・開発依頼 | 可 | 可 | 可 |
| `estimate_consultation` | 見積・相談 | 可 | 可 | 可 |
| `sales_solicitation` | 営業・売り込み | 可 | 不可 | 可 |
| `recruitment` | 採用 | 可 | 不可 | 可 |
| `partnership` | 協業・パートナー | 可 | 不可 | 可 |
| `media_other` | 取材・その他 | 可 | 不可 | 可 |

### 8.1 ポリシー強制要件

- `project_request` と `estimate_consultation` のみ、自動送信承認 UI を表示できること。
- それ以外の種別では、自動送信用エンドポイントまたは処理を呼び出してもサーバーが拒否すること。
- 問い合わせ種別は確認 UI に日本語で明示すること。
- ユーザーは送信前に問い合わせ種別を変更できること。
- 種別変更後は、それ以前に取得した自動送信承認を無効にすること。
- 本文のキーワードだけを根拠に、自動送信可能な種別へ変更してはならない。
- AI が指定した種別は確定値ではなく、ユーザーが確認・修正可能な入力値として扱うこと。

## 9. WebMCP ツール要件

初期本番公開時のツールは以下の 4 件とする。

### 9.1 `get_company_services`

| 項目 | 要件 |
|---|---|
| 種別 | 読み取り |
| 登録範囲 | 公開サイト共通 |
| 目的 | 公開中のサービス一覧と概要を取得する |
| 入力 | なし |
| 出力 | サービス ID、表示名、概要、詳細ページ URL |
| 最大件数 | 公開中の全サービス。ただし出力全体を 1,500 文字以内に要約する |
| annotation | `readOnlyHint: true`、`untrustedContentHint: false` |
| データソース | `src/data/services.ts` または同等のサーバー側アクセス層 |

#### 受入条件

- AI / DEVELOPMENT、DESIGN / BRANDING、IP / CREATIVE が取得できること。
- URL が実在する公開ページを指すこと。
- サービスデータの変更がツール結果にも反映されること。

### 9.2 `find_case_studies`

| 項目 | 要件 |
|---|---|
| 種別 | 読み取り |
| 登録範囲 | 公開サイト共通 |
| 目的 | 条件に合う公開実績を検索する |
| 入力 | `category`、`query`、`limit` |
| 出力 | 実績 ID、タイトル、クライアント、カテゴリ、要約、期間、詳細 URL |
| 最大件数 | 5 件 |
| annotation | `readOnlyHint: true`、`untrustedContentHint: false` |
| データソース | `getAllWorks()` |

#### 入力スキーマ

- `category`：任意。既存の `WorksCategory` に限定する。
- `query`：任意。1～200 文字。タイトル、クライアント、カテゴリ、詳細項目を検索対象とする。
- `limit`：任意。1～5 の整数。既定値は 3。
- `category` と `query` の両方が未指定の場合は、公開実績の新しい順または表示順で返す。

#### 受入条件

- 非公開・コメントアウト中・存在しない実績を返さないこと。
- 同じ実績を重複して返さないこと。
- 検索結果が 0 件の場合、空配列とユーザー向けの短い説明を返すこと。
- 検索語を HTML として解釈しないこと。

### 9.3 `prepare_contact_inquiry`

| 項目 | 要件 |
|---|---|
| 種別 | UI 状態更新。外部送信なし |
| 登録範囲 | 問い合わせページ表示時のみ |
| 目的 | 問い合わせフォームへ値を設定し、ユーザーが確認できる状態にする |
| 入力 | 問い合わせ種別、会社名、氏名、ヨミガナ、メール、電話、本文 |
| 出力 | 準備完了、要確認項目、自動送信対象か否か。PII の値自体は返さない |
| annotation | `readOnlyHint: false`、`untrustedContentHint: false` |

#### 動作要件

- React のフォーム state を正規の更新経路で更新すること。
- 値設定後、フォームを画面内へスクロールし、先頭の入力項目へフォーカスすること。
- AI により設定された項目であることを視覚的に識別できること。
- 既存の入力値がある場合、無確認で上書きしないこと。
- 上書きが必要な場合は、ユーザー確認または明示的な上書き指定を要求すること。
- クライアント側の既存バリデーションを実行すること。
- エラー項目をユーザーと AI の双方が理解できる形式で返すこと。
- プライバシーポリシー同意チェックは変更しないこと。
- 本ツールの実行だけでは問い合わせ API を呼び出さないこと。
- 問い合わせページを離れた時点でツールを登録解除すること。

### 9.4 `submit_project_request`

| 項目 | 要件 |
|---|---|
| 種別 | 更新・外部送信 |
| 登録範囲 | 問い合わせページかつ有効なユーザー承認が存在する間のみ |
| 目的 | ユーザーが明示承認した制作・開発依頼または見積・相談を送信する |
| 入力 | サーバー発行の承認トークンまたは同等の承認識別子 |
| 出力 | 受付 ID、成功可否、次の案内。PII は返さない |
| annotation | `readOnlyHint: false`、`untrustedContentHint: false` |

#### 実行前提

以下のすべてを満たす場合に限り実行できること。

1. 問い合わせ種別が `project_request` または `estimate_consultation` である。
2. 必須項目のバリデーションが成功している。
3. ユーザーがプライバシーポリシーを確認し、同意している。
4. 送信内容を表示した確認 UI でユーザーが承認している。
5. 承認時の内容と送信時の内容が一致している。
6. 承認が有効期限内で未使用である。
7. サーバー側レート制限を超過していない。
8. WebMCP 自動送信機能が運用上有効化されている。

#### 拒否条件

- 営業、採用、協業、取材・その他の問い合わせ
- 同意未取得
- 承認後に内容が変更された場合
- 使用済み、期限切れまたは改ざんされた承認情報
- 同一 idempotency key による重複要求
- レート制限超過
- 緊急停止中

## 10. 問い合わせ UI 要件

### 10.1 問い合わせ種別

- 既存フォームに問い合わせ種別の選択 UI を追加する。
- 選択 UI はキーボードおよび支援技術から操作できること。
- 未選択を許可せず、既定値を暗黙設定しないこと。
- 各選択肢を利用者が理解できる日本語で表示すること。

### 10.2 AI 入力状態

- WebMCP によってフォームが入力された場合、その旨をフォーム上部に表示する。
- 「AI が入力した内容です。送信前に確認してください」という趣旨を表示する。
- AI 入力状態は色だけに依存せず、テキストまたはアイコンでも示す。
- 通常入力時のデザインおよび操作を損なわないこと。

### 10.3 自動送信確認 UI

- 対象種別の場合のみ表示する。
- 会社名、氏名、メール、電話、問い合わせ種別、本文を表示する。
- メールアドレスと電話番号は確認可能であること。ただし画面外ログへ出力しない。
- プライバシーポリシーへのリンクを表示する。
- 同意チェックと承認操作を分離せず、ユーザーが両方を明確に認識できる構成とする。
- 実行ボタンの文言は、送信が発生することを明示する。
- キャンセルおよびフォームへ戻って編集する操作を提供する。
- 編集後は再承認を必須とする。
- 二重操作防止のため、送信中は実行ボタンを無効化する。

### 10.4 手動送信対象

- 営業、採用、協業、取材・その他では自動送信確認 UI を表示しない。
- 通常の送信ボタンを使用する。
- WebMCP により入力済みでも、通常の送信フロー、バリデーション、同意要件を省略しない。

## 11. API・データ要件

### 11.1 推奨構成

```text
src/
├─ components/providers/WebMcpProvider/
│  ├─ WebMcpProvider.tsx
│  └─ index.ts
├─ app/api/webmcp/
│  ├─ services/route.ts
│  ├─ case-studies/route.ts
│  └─ contact-approval/route.ts
├─ lib/webmcp/
│  ├─ schemas.ts
│  ├─ inquiry-policy.ts
│  └─ register-tool.ts
└─ types/webmcp.d.ts
```

ファイル構成は実装時に調整可能だが、ツール定義、入力スキーマ、問い合わせポリシーおよび UI を責務分離すること。

### 11.2 問い合わせ API 変更

既存 `POST /api/contact` に以下を追加する。

- `inquiryType` を必須項目に追加する。
- 許可された enum 以外を拒否する。
- 管理者通知メールおよび自動返信メールに問い合わせ種別を表示する。
- `submissionSource` を内部監査用に識別可能とする。ただしクライアント申告だけをセキュリティ判定に使用しない。
- WebMCP 自動送信時は有効な承認情報を要求する。
- 通常のユーザー操作による既存送信フローは維持する。
- 同一内容の多重送信を idempotency key で防止する。
- エラーは再試行可能、入力不正、承認不正、レート制限、サーバー障害を識別可能なコードで返す。
- 現行の最低入力時間判定だけを理由に、WebMCP の承認済み送信を「成功として応答しながらメールを送らない」処理にしてはならない。
- WebMCP 自動送信の成功は、少なくとも管理者宛通知の受付成功を確認した後に返すこと。
- ハニーポット項目は AI の入力スキーマに含めず、常に未入力とすること。

### 11.3 承認情報

- 承認情報は送信対象ペイロードのハッシュと関連付ける。
- 有効期限は 10 分以内とする。
- 1 回の送信にのみ使用できること。
- 会社名、氏名、メール、電話、本文を平文でトークンに含めないこと。
- 署名またはサーバー側保存により改ざんを検知できること。
- 問い合わせ種別または本文を変更した場合、承認を無効化すること。
- 承認情報を URL クエリへ含めないこと。

### 11.4 レート制限

- 現行のプロセスメモリ内 `Map` だけに依存しないこと。
- 複数インスタンス間で共有される永続的または分散型の制限機構を使用すること。
- 既存 Supabase の利用を第一候補とするが、同等要件を満たす別基盤も可とする。
- IP、短時間の送信回数、idempotency key を組み合わせること。
- 正常利用を過度に阻害しない閾値とし、本番ログに基づき調整可能とする。
- レート制限超過時は `429` と再試行可能時刻または待機案内を返すこと。

### 11.5 データ最小化

- 読み取りツールは公開情報のみ返す。
- PII をツール実行結果に再掲しない。
- 問い合わせ本文を分析ログ、GA4、Clarity、コンソールログへ送らない。
- 監査ログにはツール名、問い合わせ種別、結果コード、処理時間、匿名化された識別子だけを記録する。
- 問い合わせデータの保存・保持は、公開中のプライバシーポリシーおよび社内運用方針と整合させる。

## 12. WebMCP 登録・ライフサイクル要件

- `src/app/(site)/layout.tsx` 配下に公開サイト共通 Provider を配置する。
- `document.modelContext` の存在確認後にのみ登録する。
- 登録失敗はサイト表示を失敗させず、監視可能な非 PII エラーとして処理する。
- React コンポーネントの unmount 時に `AbortController` を使用して登録解除する。
- ページ状態に不要なツールは登録しない。
- 問い合わせ関連ツールは問い合わせページでのみ登録する。
- `submit_project_request` は有効な承認がある間のみ登録し、送信、キャンセル、期限切れ、入力変更時に解除する。
- 同名ツールを重複登録しない。
- ツール名、説明およびパラメータ名は簡潔で、目的が重複しないこと。
- ツール出力は原則 1,500 文字以内とする。

## 13. ブラウザ・互換性要件

- Chrome Origin Trial 対象バージョンを本番検証対象とする。
- ローカル開発では `chrome://flags/#enable-webmcp-testing` を用いた検証を可能にする。
- WebMCP 未対応の Chrome、Safari、Firefox、Edge 等で既存機能が変わらないこと。
- WebMCP 未対応をユーザー向けエラーとして表示しないこと。
- JavaScript 無効環境に対する既存サイトの対応レベルを悪化させないこと。
- Origin Trial token の期限と更新期限を運用台帳で管理すること。
- token 失効時も通常サイトが利用可能であること。

## 14. セキュリティ要件

### 14.1 アクセス境界

- `/admin` 配下では WebMCP ツールを登録しない。
- `exposedTo` に外部 origin を指定しない。
- `Permissions-Policy: tools=(self)` を配信する。
- WebMCP 用 API は same-origin を前提とし、不要な CORS 許可を行わない。
- 更新 API では `Origin` または同等の same-origin 検証を行う。

### 14.2 入力・出力

- 全入力をクライアントとサーバーの両方で検証する。
- サーバー側検証を最終判定とする。
- 既存の各フィールド文字数上限を維持または厳格化する。
- メール本文へ埋め込む値は HTML エスケープする。
- JSON、HTML、ログ、メールヘッダーへのインジェクションを防止する。
- 外部またはユーザー生成コンテンツをツール結果へ含める場合、`untrustedContentHint` を適切に設定する。

### 14.3 不正利用防止

- ハニーポット、入力時間、文字数制限を維持する。
- 分散レート制限を追加する。
- 重複送信防止を追加する。
- 自動送信対象種別の allowlist をサーバー側に定義する。
- 承認の使い回しを禁止する。
- 同一セッションから異常な準備・承認・送信回数が発生した場合に検知可能とする。

### 14.4 機能停止

- 読み取りツール、問い合わせ準備、自動送信を個別に無効化できること。
- 自動送信はコード変更なしで運用停止できること。
- 自動送信停止中も通常の手動フォーム送信を維持すること。
- 緊急停止時は、AI とユーザーに手動送信へ切り替える案内を返すこと。

## 15. プライバシー要件

- AI はプライバシーポリシーへの同意を代理してはならない。
- 同意チェックはユーザー操作でのみ変更可能とする。
- 自動送信確認画面にプライバシーポリシーへのリンクを表示する。
- 同意日時、同意対象ポリシーの版または URL を送信記録と関連付けられること。
- ツール説明に、不要なユーザー属性やブラウザ内の他サイト情報を要求する記述を含めない。
- 問い合わせに必要な項目以外を AI から収集しない。
- PII を WebMCP ツールの成功レスポンスへ含めない。

## 16. アクセシビリティ要件

- WebMCP 操作後もフォーカス位置を予測可能にする。
- フォーム入力、エラー、確認、送信中、成功、失敗を支援技術へ通知する。
- 確認 UI はフォーカストラップ、Esc キー、キャンセル操作を適切に提供する。
- 色だけで AI 入力、エラー、送信状態を表現しない。
- 既存のラベル、`aria-invalid`、`aria-describedby` を維持する。
- 200% 拡大およびモバイル幅で確認内容が欠落しないこと。

## 17. 性能・可用性要件

| 項目 | 目標 |
|---|---|
| サービス・実績 API | 通常時 p95 1 秒以内 |
| 問い合わせフォームへの値反映 | ツール実行開始から 500ms 以内（ネットワーク処理を除く） |
| 問い合わせ送信結果 | 通常時 10 秒以内 |
| ツール出力 | 原則 1,500 文字以内 |
| WebMCP 障害時 | 通常サイトの閲覧・手動問い合わせに影響しない |
| 重複送信 | 同一 idempotency key では 0 件 |

外部メールサービスの障害時は、受付成立の可否を明確にし、成立していない場合に成功表示を行わない。

## 19. 計測指標

| 指標 | 目的 |
|---|---|

| 問い合わせ準備完了率 | フォーム支援の有効性を把握する |
| 準備から確認表示への遷移率 | UI の離脱を把握する |
| 確認から送信成功への遷移率 | 自動送信フローの有効性を把握する |
| 手動送信への切替率 | ポリシーおよび UI の妥当性を把握する |
| 重複・不正・レート制限件数 | 不正利用傾向を把握する |

PII および問い合わせ本文を分析基盤へ送信してはならない。

## 20. テスト要件

### 20.1 単体テスト

- 各ツールの入力スキーマ検証
- 問い合わせ種別と実行ポリシーの対応
- 自動送信 allowlist
- 検索、件数制限、0 件処理
- 出力文字数制限
- 承認情報の生成、期限切れ、改ざん、単回使用
- ペイロード変更時の承認無効化
- idempotency key による重複防止
- PII を含まないレスポンス生成

### 20.2 結合テスト

- `getAllWorks()` と実績検索 API の連携
- サービスデータとサービス取得 API の連携
- WebMCP ツールから各 API への実行
- フォーム state、バリデーション、確認 UI の連携
- 問い合わせ API、Resend、レート制限の連携
- 通常フォーム送信への後方互換性

### 20.3 E2E テスト

- WebMCP 対応環境でのツール登録・解除
- 非対応環境での通常表示
- サービス取得
- カテゴリ・検索語による実績検索
- 依頼フォーム準備、ユーザー承認、送信成功
- 見積フォーム準備、ユーザー承認、送信成功
- 営業問い合わせで自動送信 UI が表示されないこと
- 採用、協業、取材・その他で自動送信できないこと
- 承認後の本文変更で再承認が必要になること
- フォーム表示から 2 秒以内に承認操作が完了した場合でも、承認済み送信が黙って破棄されないこと
- 二重クリックで 1 件だけ送信されること
- レート制限時の案内
- 自動送信停止時に手動送信へ切り替えられること
- モバイルおよびキーボード操作

### 20.4 AI ツール選択評価

最低 30 件の評価プロンプトを用意し、以下を含める。

- 明示的なサービス質問
- 曖昧な課題相談
- カテゴリ指定の実績検索
- 業界・課題だけを指定した実績検索
- 制作依頼
- 見積相談
- 営業・売り込み
- 採用問い合わせ
- 協業問い合わせ
- 取材・その他
- 問い合わせ送信を意図しない単なる情報収集
- 悪意ある指示、過大な入力、種別偽装の試行

評価では以下を確認する。

- 正しいツールを選択すること
- 不要な更新ツールを選択しないこと
- 正しい問い合わせ種別を提案すること
- 自動送信不可種別を自動送信しないこと
- 必須パラメータを正しく設定すること
- ツール失敗時に無限再試行しないこと

## 21. 受入基準

以下をすべて満たした場合、本番公開可能とする。

| ID | 受入基準 |
|---|---|
| AC-01 | WebMCP 対応環境で 4 ツールが定義どおり登録される |
| AC-02 | 未対応ブラウザで表示・操作・手動問い合わせに回帰がない |
| AC-03 | `/admin` で公開 WebMCP ツールが 1 件も登録されない |
| AC-04 | サービス取得結果が公開ページと一致する |
| AC-05 | 実績検索が非公開データを返さず、最大 5 件に制限される |
| AC-06 | 問い合わせ準備だけでは外部送信が発生しない |
| AC-07 | プライバシー同意を AI が変更できない |
| AC-08 | 制作・開発依頼と見積・相談は、ユーザー承認後に 1 件だけ送信される |
| AC-09 | 営業、採用、協業、取材・その他は自動送信できない |
| AC-10 | 承認後の入力変更により承認が無効になる |
| AC-11 | 期限切れ、改ざん、使用済み承認が拒否される |
| AC-12 | 複数インスタンスで有効なレート制限が導入されている |
| AC-13 | ログおよび分析イベントに PII・問い合わせ本文が含まれない |
| AC-14 | 自動送信を停止しても通常フォーム送信を利用できる |
| AC-15 | 単体・結合・E2E テストが成功する |
| AC-16 | AI ツール選択評価で重大誤動作が 0 件である |
| AC-17 | Origin Trial token と Permissions-Policy が本番で正しく配信される |
| AC-18 | 運用担当者が停止・復旧手順を実施できる |
| AC-19 | WebMCP 自動送信の成功表示時に管理者宛通知が実際に受け付けられている |

重大誤動作とは、無承認送信、自動送信不可種別の送信、PII 漏えい、重複送信、管理機能の露出を指す。

## 23. ロールバック・緊急停止

以下の優先順で停止可能とする。

1. 自動送信だけを停止し、手動送信へ切り替える。
2. 問い合わせ準備ツールを停止する。
3. すべての WebMCP ツール登録を停止する。
4. 必要に応じて Origin Trial token の配信を停止する。

停止条件の例：

- 無承認送信または自動送信不可種別の送信が 1 件でも発生した場合
- PII がログまたはツール出力へ含まれた場合
- 重複送信が継続発生した場合
- 問い合わせ API の障害率が運用閾値を超えた場合
- WebMCP が通常サイトの表示・操作へ影響した場合

復旧時は原因、影響範囲、修正、テスト結果を記録し、読み取り、準備、自動送信の順に再開する。
