# Claude Code 生産性ハック集

> このプロジェクトを通して身につけてほしい開発スタイル。
> Claude Code の真価を引き出すコツを集めた。
> 全部覚えなくていい。気に入ったやつから使ってみて。

---

## H01. コードを書く前に「方針」を MD で出させる

実装に入る前に、Claude に MD で構造提案を出させる。
- セクション分解
- 要素の階層
- 余白・フォント
- SP 対応

これが揃ってから実装に入ると、書き直しが激減する。
本プロジェクトでは `/capture-image` スキルがそれを自動化してる。

---

## H02. CLAUDE.md は 200 行以内、目次に徹する

CLAUDE.md は **毎ターン読まれる**。500行書くと毎ターン500行のトークンを消費し、しかも認知負荷の上限（150〜200命令）を超えて約7割が無視される。詳細ルールは `.claude/rules/` に切り出して、CLAUDE.md は IF-THEN 目次。

---

## H03. ミスったら rules/ に追記

Claude が同じミスを繰り返すなら、それはルール不足。
該当 rules ファイルにアンチパターンを足す。
次から同じ場面で回避される。**Compounding Engineering** と呼ばれる発想。

---

## H04. 独立タスクは並列サブエージェントで

1人の Claude に「SCSS全部見て、アセットも整理して、rules/ も書いて」と全部やらせると遅い。
独立タスクは別のサブエージェントに投げて並列実行する。3〜5倍速い。
本プロジェクトの引き継ぎ準備も Wave 1〜3 で並列に組んだ。

---

## H05. build / lint は Claude にやらせる

`npm run build` を Claude に走らせて、出たエラーをそのまま渡してデバッグさせる。
ターミナル切り替えの認知負荷が減る。
バックグラウンド実行（`run_in_background`）にすれば他の作業と並行できる。

---

## H06. アンチパターンを先に列挙させる

「このセクション実装する前に、ありがちなミス5個挙げて」と聞く。
そのまま実装ガイドになる。
特に「fluid() 化忘れ」「色の直書き」など、自分が踏みがちなパターンを Claude が事前に警告してくれる。

---

## H07. コミットメッセージは Claude に下書きさせる

`git diff` を渡して「日本語で `Phase X: ...` 形式で」と指示。
ただし **最終的には自分で内容を確認** してから commit。
diff が大きい時ほど Claude の要約が効く。

---

## H08. rules/ にプロジェクトの掟を書く

- カラーは CSS 変数経由のみ
- スケーラブル値は fluid() のみ
- Component/Component.tsx + .module.scss + index.ts の 3 点セット
- ...

これを書いておくと、Claude が「このプロジェクト用に最適化された Claude」になる。

---

## H09. スキルは 100% 動くものだけ入れる

70% 動くスキル 10 個より、100% 動くスキル 3 個。
動かないスキルは即消す。
"If an automation doesn't work 100% of the time, it's not really an automation." の原則で行く。

---

## H10. hooks は「絶対に忘れちゃダメなこと」だけ

便利系の hook を 20 個入れると起動が 4〜5 倍遅くなる（実測値）。
本プロジェクトは初期段階なので hooks は入れていない。
必要になったら以下から始める:
1. Write/Edit 直後の Read 強制
2. 危険コマンドのブロック（`rm -rf` 等）
3. セッション終了時のミス追記

---

## H11. docs/ は人間用、rules/ は Claude 用

役割を分けると、両方が腐らない。
- `docs/` … 詳細ドキュメント（人間が腰を据えて読む）
- `.claude/rules/` … Claude が状況別に参照する短いガイド

両方に同じこと書くと整合性が取れなくなって地獄。

---

## H12. 迷ったら Claude に聞く

Stack Overflow より早い。聞き方:

- 「このコード、もっと簡潔に書ける？」
- 「このレスポンシブ崩れの原因を絞り込んで」
- 「next/image の priority を付けるべき場所教えて」

**該当ファイルを Read させながら** 聞くと精度が上がる。
ふわっと聞かない、具体的なファイルパス・行番号を添える。

---

## このプロジェクト固有のハック

### 新セクション追加の最速フロー

1. Figma スクショを撮る
2. `/capture-image` を呼ぶ
3. 提案を確認 → "GO"
4. `npm run dev` で表示確認
5. 320 / 768 / 1200px の 3 点で目視
6. `npm run lint` → コミット

平均 30〜60 分でセクション 1 つ。

### 新色追加の作法

1. `src/styles/_variables.scss` に CSS 変数追加
2. `.claude/rules/design-tokens.md` の表に 1 行追記
3. SCSS から `var(--color-xxx)` で参照

色を増やしたら必ず 2 ファイル両方触る。片方だけだと Claude が認識できない。

### Figma 値が読めない時

スクショ + 「この見出しのフォントサイズ推定して」と Claude に投げる。
正確値がなくても、画像から推測してくれる。たたき台としては十分。
あとで Figma で実測したら fluid() の max を更新するだけ。

### コミット直前の儀式

`.claude/rules/pre-commit-checklist.md` を Claude に読ませて
「この diff、チェックリスト通りか確認して」と聞く。
うっかりの色直書き・固定 px が即見つかる。

### 並行作業の組み方

ファイル単位で衝突しないタスクは同時に走らせる。例:
- A: SCSS の色置換 → `*.module.scss` のみ
- B: `.claude/rules/` 整理 → `.claude/` のみ
- C: アセット移動 → `public/` + src/ の参照置換

同じファイルを触るタスクは順次。これは引き継ぎ準備で実証済み。

---

## アンチパターン（やったら直す）

- ❌ いきなりコード書き始める → ✅ 先に Claude と方針を作る
- ❌ 同じミスを 2 回やる → ✅ `.claude/rules/` に追記
- ❌ 全部 1 人の Claude にやらせる → ✅ 独立タスクは並列に
- ❌ CLAUDE.md に全部書く → ✅ 目次に徹して詳細は rules/
- ❌ docs/ と rules/ で同じこと書く → ✅ 役割分離
- ❌ Figma 値が無いから手が止まる → ✅ Claude に推測させて、たたき台で進める
- ❌ npm エラーをコピペで Stack Overflow 検索 → ✅ そのまま Claude に貼る
